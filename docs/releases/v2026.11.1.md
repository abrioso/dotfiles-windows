## Compatibility and migration

- Group selectors use toggles on supported consoles. Use `configure.ps1 -TextMode` for the text
  fallback. Scalar prompts retain their existing input style. First-run missing JSON files are
  initialized before editing; cancellation can leave those initial defaults in place.
- Existing machine-local JSON remains local. Review the selected groups with `setup.ps1 -Plan`
  before apply; keep package prerequisites ahead of dependent groups.
- The Ollama start/stop helpers now require `-ComposePath`. Keep the original file directory,
  project name and volume definitions when adopting an existing Compose stack. Review a legacy
  file before adding the managed marker. New generated files bind ports to localhost and leave
  Watchtower behind the opt-in `automatic-updates` profile; existing files are preserved.
- `Start-OllamaAndWebUI.ps1` now terminates with migration guidance. Its direct-run volumes differ
  from the Compose volumes. Back up and explicitly map existing data before migration; the
  helpers do not move or delete legacy containers/volumes automatically. See the
  [Ollama lifecycle migration guide](../../powershell-scripts/README.md#ollama-compose-lifecycle).
- The Compose helpers require Docker Compose with `up --wait` support. GPU and application
  readiness still require runtime acceptance on the intended host.
- Diagnostic `Unknown` remains inconclusive, never a pass. Unregistered Ubuntu and an ASCII-only
  profile can legitimately be `Skipped`. Font checks establish consistency with local completion
  metadata, not independent authenticity of that mutable metadata.

2. Review the evidence and mark the draft release PR ready only after the manual gate is met.
3. Merge `release/v2026.11.1` into `main` with a merge commit after required checks pass.
4. Reconcile these release-only documentation/stabilization commits into `develop` through a
   second merge-commit PR from the same release branch.
5. Verify the production merge, tag that commit `v2026.11.1`, and publish the matching GitHub
   Release with tested Windows builds, evidence references and known limitations.
6. Delete the release branch only after production, reconciliation, tag and release are verified.
